## Область и ограничения

Проверены цепочки Telegram → поиск/черновик → публикация, инструменты управления,
очереди и запуск Windows, каталог и варианты товара, фотографии, ручной CRUD
Filament и RU/CS. Для поиска/обучения повторно проверены диагностические сценарии
из [предыдущего аудита](2026-09-20-photo-chain-review.md).

Это аудит, не исправление production-кода. В рабочем дереве сохранены незавершённые
изменения Filament/CRUD/локализации. Рабочая БД, фотографии пользователя и воркеры
не изменялись; платных вызовов и поисков на магазинах не было. Проверка не означает
прочтение каждой строки зависимостей, полноценный security-аудит или доказательство
работы на всех магазинах.

## Новые подтверждённые проблемы

### 1. P1 — запуск может оставить принятый товар без фото

`scripts/start-ningredy.ps1` вызывает `bot:clear-stale`.
`app/Console/Commands/ClearStaleBotWork.php:49–52` удаляет все задания из `jobs`,
включая `StoreProductImages` для уже принятого товара. Публикация и перенос файлов
в каталог разделены очередью.

Воспроизведение: опубликованный товар + принятый черновик + реальная задача
переноса в database-очереди → команда очистки → задача исчезла, товар остался
опубликованным без media. Это объяснимый механизм потери переноса, но не доказанная
причина конкретного старого пользовательского инцидента.

Исправлять: отделить отменённый поиск от обязательного завершения публикации;
не удалять задания переноса/сохранения вместе с поиском. Перенос должен быть
повторяемым и восстанавливаемым.

### 2. P1 — откат удаления не восстанавливает фотографии

`app/Models/Product.php:34–36` удаляет каталог файлов в событии `deleting`,
до подтверждения транзакции БД. Аналогичный риск есть в файловых событиях media.

Воспроизведение: удалить товар внутри транзакции, затем выбросить исключение:
товар восстановился откатом, файл остался удалённым.

Исправлять: надёжная очистка после commit, с отдельной повторяемой задачей;
при необходимости промежуточное обратимое перемещение. Не считать файловую
систему частью транзакции БД.

### 3. P1 — текстовый инструмент обходит защиту чужого черновика

`app/Ai/Tools/ReviewProductDraft.php` ищет черновик по ID и проверяет статус,
но не принадлежность оператору/чату и не подтверждение отклонения, используемые
путём Telegram-кнопок. Это проблема среди допущенных администраторов, не заявление
о доступе неавторизованного внешнего пользователя.

Воспроизведение: инструмент оператора 111 отклонил черновик оператора 222.

Исправлять: общая прикладная проверка прав, актуальности и подтверждения для
кнопок и AI-инструментов. Если нужен доступ администратора к чужим черновикам,
оформить его явно, а не случайным обходом.

### 4. P2 — неудачная операция стирает собственный журнал

`app/Ai/Tools/Concerns/RecordsOperations.php:40–74`: запись операции и запись
ошибки находятся в той же транзакции, из которой исключение выбрасывается наружу.
Откат удаляет и диагностическую запись.

Воспроизведение: callback бросает исключение → в `ai_operations` нет записи
неудачной операции. Откат бизнес-изменений правильный, потеря аудита — нет.

Исправлять: сохранять исход ошибки вне откатываемой бизнес-транзакции.

### 5. P2 — повтор задания сообщает успех, не повторив задание

`app/Ai/Tools/RetryFailedJob.php:35–39` передаёт числовой ID в `queue:retry`.
Настроенный `database-uuids` ищет UUID. Команда при ненайденном задании может
завершиться с кодом 0, который инструмент ошибочно принимает за постановку.

Воспроизведение с настоящей Artisan-командой: `queued=true`, failed-запись
осталась, очередь ничего не получила.

Исправлять: правильный идентификатор провайдера и проверка фактического результата.

### 6. P2 — фильтр каталога выбирает один вариант, карточка показывает другой

`CatalogController::applyFilters()` отбирает товар через подходящий вариант,
а `ProductCardPayload::for()` выбирает default/первый из всех доступных вариантов.

Воспроизведение: фильтр Black и цена до 1500, подходящий вариант стоит 1000;
карточка возвращает цену default White — 3000.

Исправлять: передавать выбранный подходящий вариант в карточку и ссылку;
согласовать с этим сортировку по цене.

### 7. P2 — Telegram показывает неактивный вариант

`app/Services/Telegram/ProductCardPresenter.php:73` использует `defaultVariant`
без согласованного с публичным каталогом отбора доступности.

Воспроизведение: default отключён, стоит 999; активный вариант стоит 777;
Telegram показывает 999. Общий выбор допустимого варианта нужен обоим интерфейсам.

### 8. P2 — отменённая фотография всё ещё оплачивает распознавание

`app/Jobs/TranscribeTelegramPhoto.php` не проверяет отмену/processed_at до
скачивания и вызова модели. Воспроизведение: отменённый update скачивается,
распознаётся, получает статус `transcribed` и отправляет следующее задание.

Следующее основное задание защищено processed_at: тест НЕ доказывает запуск
нового поиска. Доказаны лишняя обработка, вызов модели и изменение статуса.
Аналогичный голосовой путь требует той же проверки отмены.

Исправлять: проверка актуальности перед и после внешних вызовов, общая для
мультимодальных входов и основного обработчика.

### 9. P2 — галерея товара не связана с выбранным вариантом

`ProductController` возвращает media без `product_variant_id`;
`resources/js/Pages/Products/Show.vue` меняет вариант, но использует общую галерею.

Воспроизведён payload двух вариантов разных цветов с двумя фото без привязки
фото к вариантам; клиентский код подтверждает отсутствие фильтрации.

Исправлять: сохранять привязку в payload, показывать фото выбранного варианта
и явно общие фото, не смешивать цвета автоматически.

## Дополнительный риск, подтверждённый чтением кода

### P1 — стартовый cleanup способен остановить другой проект

`scripts/clear-leftover-processes.ps1:46–62` ищет процессы по относительным
командам `artisan schedule:work`, именам очередей и `browser-server.mjs`, затем
вызывает `Stop-Process -Force`. Каталог проекта не установлен. Комментарий самого
скрипта прямо признаёт совпадение с другим Laravel-проектом/checkout.

Разрушительный сценарий не запускался. Исправлять через владение процессами:
проектный instance ID, зарегистрированные PID с проверкой времени старта и
командной строки, абсолютные пути запуска. Не расширять глобальные kill-паттерны.

## Telegram CRUD — конкретный следующий объём

Уже есть инструменты поиска, редактирования товара/варианта, фотографий,
черновиков, удаления с подтверждением, состояния и повторов заданий. Но нет
полного удобного создания товара вручную и общего последовательного интерфейса.

1. Общие прикладные команды для Telegram-кнопок, AI tools и админки:
   права, целевой товар/вариант, актуальность, валидация, журнал до/после,
   повторяемость запроса. Агент понимает свободный текст; сервер надёжно исполняет.
2. Меню карточки: «Изменить», «Фото», «Скрыть/Показать», «Удалить» с подтверждением,
   «Назад». Редактирование цены/остатка выбирает конкретный вариант товара.
3. «Добавить вручную»: название → категория → закреплённые атрибуты категории
   → значения → фото → предпросмотр → подтверждение. Без обязательного SKU/slug,
   без веб-поиска, если админ его не просил.
4. Характеристики: переиспользовать существующие значения или ввести новое;
   использовать те же правила и настройки категории, что в Filament.
5. Фото: загрузить альбом прямо в выбранный товар, переставить, выбрать главное,
   удалить с подтверждением. Не отправлять каждое вложение в поиск автоматически.
6. Состояние диалога привязать к чату, оператору, товару/варианту и актуальной
   операции; «Назад»/«Отмена» работают и при ожидании фото/текста.
7. Списки, кнопки навигации, статус очереди — без вызова LLM. Естественный язык
   остаётся дополнительным способом управления, не обязательной платной прослойкой.
8. Тесты: разные операторы, старые кнопки, двойное нажатие, прерванная загрузка,
   откат БД, повтор задания, смена варианта и ручное добавление без поиска.

## Рекомендуемый порядок

Сначала сохранность публикации/файлов и единые проверки управляющих действий.
Затем согласованность вариантов/атрибутов и оставшиеся дефекты фото-цепочки.
После этого расширять Telegram CRUD на уже общих надёжных командах.
Не лечить эти ошибки новыми ограничениями количества фото, списками доменов
или урезанием автономности тренера: причины здесь в состоянии и исполнении.
